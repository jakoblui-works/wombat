# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Cursors follow one rule everywhere: a pointer on buttons, tabs and rows, not-allowed on disabled controls, resize cursors on sashes (at their limits too), and an arrow on empty chrome and the title bar.
- An agent's reply shows at an even pace while it streams, about 300 characters a second, instead of in bursts; when it falls more than about two seconds behind, the rest shows at once. A reply keeps that pace after a tool call follows it or the turn ends, until it has caught up. A half-typed code span, emphasis, link or code fence line is held back until it closes, so no stray markup flashes. Replies that are finished when a chat opens, and every reply when the system asks for reduced motion, show as they are.
- Motion where something changes, all of it off when the system asks for reduced motion. New chat messages fade and slide in (the ones there when a chat opens don't); the working line's dot pulses and its words fade when the activity changes; the Working mark spins and a row's mark fades when the state changes; a row moving to another group in the agents list slides there; Reasoning, tool calls, answered permissions and the plan expand and collapse; menus and popovers fade in about 0.1 s when opened with the mouse and appear at once when opened with the keyboard. Hover colours change in 80 ms. Nothing moves on typing, tab clicks, switching activity, panel resizes or tab drags.
- The settings lists are listboxes (arrows move a highlight, ringed while the list has focus and apart from the current value's mark; Enter or a click picks); the context dialog asks again by itself once the agent is idle, opens at once with "Loading…" when typed before the tools are known, and shows shares with one decimal ("0.3%", "<0.1%").
- With Claude Code, `/context` shows Claude's own colour for each category, and `/memory` and `/agents` beside the memory files and custom agents.
- The agent service reports an agent's context breakdown on request (`POST /agents/:id/context`): the model, tokens used out of the window, the usage by category, and lists of memory files, custom agents, skills and MCP tools (paths in your home shown with `~`). It runs `/context` as a hidden turn that leaves nothing in the chat, the log or the agent list, only when the agent lists `/context` among its commands; while a turn runs it answers `busy`, and for a tool or agent that can't report one, `unsupported`. Asked again while a report is under way, it answers with that same report. `GET /harnesses` lists each tool's `features` (`context` for Claude Code).
- The agent service tracks each agent's prompt cache: `GET /agents` shows how long it lives (5 min or 1 h) and when it was last used, so the app can show the time left. It is kept in memory only, never stored.
- A status bar along the bottom of the app shows the agent service ("Service · running 6 h 15 min · 1 agent"), amber with a warning when it runs older code than the app ("older than the app") or doesn't match this app's version, "connecting…" while it connects, and "not connected" in red when it can't be reached. Screen readers announce each change. Clicking it opens a panel with when it started, why it isn't connected, the agents with a process (while connected), and Stop service and Restart. When the app finds a service already running as it starts, a notice says since when (or, for a service too old to say, only that it was running) and, if it is older than the app, offers Restart. A service the app started itself brings no notice, and a dismissed notice stays away, also after a reload of the window, until Wombat starts again. File has a new Restart Service item.
- The footer's settings are a button naming the model and effort ("Opus 5.5 · High") that opens a settings dialog, and the mode has its own button. The dialog lists every setting under its name as a heading, with its description below: choices as a list with a check on the current one, effort as a stepped slider (it stays on a pick until the agent takes it or refuses it), on/off settings as switches. A pick applies at once and the dialog stays open. A change the agent doesn't answer within 30 s fails with a message that says so and what to do. A tool can bring its own footer parts, and can hide settings from the dialog (Claude Code's `agent` setting is hidden).
- A stopped chat goes on: a message, a setting or `/context` sent to an agent without a process (stopped, crashed, or from before a restart of the service) starts it again in the same Claude session, which remembers the conversation, and its reply lands in the same chat. The model, effort and other settings it had are set again; if the agent doesn't answer one, it and the rest are skipped, and the agent stays usable. While it isn't running, the footer shows "Not running" in place of the context ring (its tooltip: "Your next message starts it again"), the settings stay usable and say "Starting…" while a pick starts it, and an open settings dialog stays open. If the agent can't take up its session, the message stays, its turn ends as failed with a message that says what to do, and the next message tries again. `GET /harnesses` lists `resume` for tools that can do this (Claude Code); an agent of a tool that can't keeps a read-only message box, and the indicator's tooltip says to start a new agent. While the app is still reading which tools can do this (or couldn't read it), a stopped agent's chat stays usable.
- The context ring warns before the limit (amber from 80 %, red from 95 %) and shows the prompt cache: its tooltip adds "Cache 1h · 42 min left" (counted down every 30 s), and the ring (not its percentage) dims once the cache has expired.
- Typing `/context` opens a "Context usage" dialog for tools that offer it (Claude Code): the model, tokens used out of the window, a bar and table of the categories, and the lists of memory files, agents, skills and MCP tools. It leaves nothing in the chat, and while the agent works it says "Available once the agent is idle".
- A footer under the message box: the agent's tool (picked in New agent, fixed for the chat), its settings (a settings button and the Mode button; shown as the agent reports them, changeable at any time, a refused change says why under the footer) and a context ring, with a clearly visible track and the share as text ("3%"), whose tooltip (after 200 ms) gives the tokens used out of the window.
- A working agent says what it is doing: its chat shows a line above the message box ("Thinking…", "Writing…" or "Running <tool>") and its row in the Agents list a second line ("Working · Running Bash").
- The Agents sidebar lists the agents grouped by state (Waiting on me, Working, Done, Error; stopped agents under Done) with title, folder, branch, an excerpt of the agent's own latest message as its chat shows it (a sub-agent's text doesn't show there) and the time since you last interacted. A row opens or focuses the agent's chat tab; its menu stops the agent while its process runs (done agents too, and agents whose turn failed) or deletes it (delete asks first). New agent picks the tool and the folder (the workspace root first, then its repos; the last one used by default) and takes the first message. The service lists those folders at `GET /repos`.
- An agent's chat: messages as Markdown with highlighted code, tool calls as one line each that expand to their input, output and text (long texts clipped, saying how much was left out), reasoning collapsed, and the agent's plan pinned on top. Permission requests are answered where they appear (Approve, Reject and any other option); answered ones show the outcome. The message box sends on Enter (Shift+Enter for a new line), keeps your text when a send fails, and has Cancel while the agent works. The header has Stop (while the process runs) and Delete. Agent content stays text: raw HTML shows as written, only https links are links (opened in your browser), and images never load.
- Edit approvals: an agent's request to edit a file shows in the chat as a card with the file, its +/− line counts, the changed lines with three lines of context, and Approve and Reject; a change too large to show there is reviewed side by side. "Open side by side" opens the edit in a diff tab beside the chat (Monaco's diff editor, read-only) with the same buttons; answering in either place shows the outcome in both. An answered request's diff tab stays until you close it and doesn't reopen on the next start. A permission request and the tool call it asks about show as one item; once answered, it expands to the tool call's output. A tool call's diff (an edit that wasn't asked about) shows as the same compact diff.
- Needs me: the right sidebar lists every waiting agent's open permission requests (or "Waiting for you" when it has none), newest first, with the agent, what it asks and the time since. A click, like a click on a notification, switches to Agents and opens the agent's chat scrolled to the request (the oldest one for a notification). The title bar's Needs me toggle shows how many wait.
- An integrated title bar: the File, Edit, View and Window menus on the left (each item shows its key), the workspace name in the middle (drag the window by it), the Needs me toggle and the window's own controls on the right. The Edit items act on the field you were typing in. The page itself can cut, copy or paste only right after a click or key press in its window.
- Splits that open an empty group: a split button on each group's tab bar (click splits right, Alt+click splits down), a tab's context menu (Split Up, Down, Left, Right, and Close) and the tab bar's own context menu, beside the tabs (the four splits, and Close Group) act on the tab or group you used them on, and the new group is the active one, ready for the next thing you open. The commands are `view.split.right|down|left|up` and `view.closeGroup`. Empty groups are saved with the layout; Close Group and Ctrl+W close a group that has no tab (never the last group).
- The app scaffold: a pnpm workspace with shared types, the agent service and the desktop app.
- The agent service's API, on 127.0.0.1 only: start a Claude Code agent in a repo of the workspace, send it messages, answer its permission requests, cancel a turn, and stop or delete the agent, with a stream of alerts whenever something changes: an agent, a proposal, or an item or a binder's settings (an `items` alert, also for an edit you make by hand). Every request needs the token from the discovery file.
- Agents use your own `claude` login. They get only an allowlisted environment: never the service's token, its `WOMBAT_*` settings or `ANTHROPIC_API_KEY`; `CLAUDE_CONFIG_DIR` is passed on when it's set.
- Agent history is kept in `$XDG_STATE_HOME/wombat/service.db` (`~/.local/state/wombat/service.db` by default, only you can read it), so it survives a restart of the service.
- Each agent runs in its own systemd user scope in `wombat-agents.slice`, so stopping or deleting it ends everything it started. The service stops anything left in that slice when it starts and when it shuts down. Without a usable systemd user manager, agents run as plain process groups and the service logs a warning.
- The agent service runs as a process: configured by `WOMBAT_WORKSPACE` (required), `WOMBAT_PORT` (default 14900, 0 for any free port) and `WOMBAT_STORE`; it writes `$XDG_RUNTIME_DIR/wombat/service.json` (only you can read it) so the app can find it, lets only one instance run per runtime folder (a second start names the running one and exits 0; the lock of a service that died is taken over), logs to stderr only, and on SIGINT or SIGTERM stops its agents and removes the file.
- Items: choose a folder of binders and item files as the items root, in the app with the Desk's Choose items folder… button or Choose Items Folder… in the File menu (saved per workspace; the service restarts with it, and a folder that can't be read is refused and the old one kept), or with `WOMBAT_ITEMS` when you run the service on its own, and the service lists the binders (`GET /binders`), a binder's items (`GET /binders/:id/items`) and one item by id, handle or old handle (`GET /items/:ref`), invalid items included with their problems. Each item comes with its binder's id and an excerpt of its body: the first paragraph, without a leading list, quote or heading marker, on one line and at most 1,000 characters, ending in "…" when cut (none when the body has no text or the file can't be parsed). A list or board view takes `excerpt: false` to draw its rows as titles only; `GET /binders` sends it with the view. A binder is a folder with a `_binder.yaml`; a folder still holding the old `_structure.yaml` lists a problem saying to rename it, or to delete it when a `_binder.yaml` is beside it; without a `_binder.yaml` the folder's files are in no binder until it's renamed. Without an items root these routes answer `items_not_configured`. You create, change and delete items over `POST /binders/:id/items`, `PATCH /items/:ref` and `DELETE /items/:ref`, checked like agents' writes but without access levels or locks; each change names the version you read, and a stale one is refused with nothing written. `POST /binders` creates a binder: it writes a starter `_binder.yaml` (the name's slug as id, read access, one list view) in a new or existing folder, and refuses a taken id or prefix, a folder that is already a binder, and a folder a `naming: free` binder's include reaches, with nothing written. Agents change items through their tools.
- Agent tools: with an items root (chosen in the app, or `WOMBAT_ITEMS` when the service runs on its own), every agent gets Wombat's ten item tools over MCP at `/mcp` to describe the binders, search, read, create, update and delete items, or propose those changes. A binder's access level (`hidden`, `read`, `propose` or `edit`) decides what an agent sees and may do, and locked fields can't be changed by an agent. Claude Code pre-allows the wombat tools, so it doesn't ask before each call.
- Agent token: each agent gets its own token for `/mcp`. It opens only `/mcp` (never the app's routes), is kept only in memory, and is revoked when the agent stops, is deleted or the service exits.
- Agents propose changes to plain text files with `propose_change`: edits to an existing file or the whole text of a new one, at any path (a path outside the workspace is marked, not blocked). The file stays as it is until you approve. A file the items own is refused, and an agent has at most 20 open proposals and 512 KiB of text per proposal, with a reason of at most 4 KiB (yours on a reject too) and at most 100 edits per call, each `old` at most 64 KiB. Agents revise a proposal you haven't decided yet with `revise_proposal`, which adds a version to it (a conflicting file edit or item update is rebuilt on the file or item as it is now, and the answer says `rebuilt`); once a proposal has 50 versions, your drafts counted, the agent's revise is refused (your drafts and approve's re-applied versions never are). Both tools work with or without an items root. See `docs/proposals.md`.
- An agent learns how you decided its proposals with your next message to it: a note in front of the message lists each approved, rejected (with your reason) or conflicting proposal once, with your own changes as a short diff, and names the proposal your message is about (`proposalId`). A decision alone never starts a turn, and a message that starts with `/` carries no note. The note is kept in the agent's log as a `proposal_note` entry.
- Proposals: every open proposal shows in the Needs me sidebar as a row in a "Proposals" group below the agents' requests, with its file's full path or its item (marked "outside workspace" when it is), what it does when it isn't an edit ("new file", "new item" or "delete"), the agent's title, "edited" once your version is current, its age, and, for a file, Approve and Reject; the title bar's count includes them. An item proposal is decided in place, in the Desk's views, so its row has no buttons: a click opens its binder in the Desk's sidebar on its first view with the proposal revealed, and a proposal whose binder is gone or broken opens its tab instead. A conflict row offers only Reject. A proposal opens as a tab from a file proposal's row in Needs me, from an item proposal's mark or proposed row in the Desk's views and Open the diff in the item's tab, and from an item proposal's row in Needs me when its binder is gone or broken. The tab shows a file's diff with line numbers (the file as it is now against the proposed text, empty on the left for a new file) or an item's changed fields, one row each with the item's value beside the proposed one (links as handles; a new item's rows all new, a delete's the item as it is), the agent's reason, Approve, and Reject with an optional reason of your own; a new item's tab is named by its proposed title. A pending file proposal's proposed text is editable in the tab: type into it or drop a single change with the gutter's arrow, and your version is saved as you go (each line keeps its own line ending, and the file its byte order mark or none) and is what Approve writes; Approve waits for the save, with the text read-only meanwhile, and approves nothing when it fails. Edits not saved yet when the proposal is decided elsewhere (its row's Approve) aren't in it, and the tab then shows what was decided and says so. A pending item proposal is editable the same way: a property in its row (a list for options and links, a text box otherwise), the title and the body in the diff, one at a time, and any field dropped from your version and brought back; a value the service refuses shows its problem at the field, and Approve stays off until it's fixed (your version saved before stays). The tab's version list shows every version (yours marked "you"), with who made it, when and why, and opens an earlier one read-only. When the agent revises, the tab shows its new version and says so, and where your edits are: in the previous version, or not kept when they weren't saved yet. The tab warns when the file changed since the current version was made (`GET /proposals/:id` says `baseChanged`): Approve then applies the agent's edits to it again where they still fit and otherwise ends in a conflict, and on your own version, which holds no edits to apply again, ends in a conflict (keep a copy of your text, then reject or ask for changes); it also warns when the file can't be read now, shows why a proposal couldn't be applied (an item's at the field it names), follows the agent's revisions, and shows the outcome once decided; an open proposal's tab comes back at the next start. "Ask for changes" in the tab (disabled when the agent is stopped or deleted, its chat can't take a message, or the proposal can't be revised) opens the agent's chat with the proposal as a chip above the message box (a button removes it); the message you send carries it, and the chip stays until a send is accepted, also when the send is refused (a proposal decided while the chip waited: remove it and send again). The chat shows what the agent was told as one quiet line before your message, "Told the agent: 2 approved, 1 rejected" and/or "Asked about <the proposal's file or item>", which expands to the outcomes and your changes as a diff. A proposal from an agent, for a file or an item, is stored in the service's store and sends a `proposal` alert at each change. The service lists them (`GET /proposals?status=`), shows one with every version (`GET /proposals/:id`), approves (`POST /proposals/:id/approve`, naming the version you saw) or rejects them, and keeps your own version of a pending proposal (`PUT` and `DELETE /proposals/:id/draft`; item fields that don't pass answer with their `problems`, by field). Approving never overwrites a change made since: a file whose edits still fit gets them applied again as a new version to approve, a path that leads somewhere else now (a folder on it replaced by a symlink) is never written through, and anything else becomes a `conflict` with the reason (an item is re-checked at the version the agent read and under the binder's settings as they are now). A proposal is written exactly once, also when the service dies in the middle: at the next start it is settled from what the target holds. A proposed create in a free-named binder carries its file path in its own `file` field (null for every other proposal), apart from its `fields` (title, body and properties), so a property named `file` is proposed like any other.
- The Desk: an activity whose sidebar shows your binders as a tree that follows their folders. The folders on the way to a binder are drawers, which open and close with a click or the arrow keys; a binder inside another binder's folder shows under it; drawers and binders are sorted by name, and items never appear in the tree. A binder's row shows its item count and how many items are invalid; a binder whose `_binder.yaml` is broken shows its folder name and what is wrong, and the others stay. A hand edit of a `_binder.yaml` shows in the tree within about a second. A click (or Enter) opens a binder on its first view, or a binder without views as all its items in one list by handle number, in the sidebar in place of the tree, with a back arrow to the tree and the binder's views above it, one click each. Only the sidebar's tree or list scrolls; its header and the binder's views stay in place. A list view shows the items its `filter` matches (a link matches by handle or id), sorted by its `sort` properties in order (numbers and dates ascending, select options in their listed order, text as you'd read it, with no value or a value that doesn't fit last, ties by handle number), and with `group` under one header per option, or per value, then one for the items without a value; a header shows its item count and folds and unfolds its items with a click or the arrow keys (every group open when the view opens; folding isn't saved); a tree view nests each item under the item its `parent` link names, at the top when that item is missing or filtered out, its rows opening and closing with a click on the arrow or the arrow keys. A board view shows as a list grouped by its `column` property, with its filter and sort. A list group's count includes only items, not proposed new items or missing ones. An item in a list (or a board) shows one text, wrapped onto as many lines as it needs: its whole first paragraph when its body starts with its title, else its whole title, with a hairline between items; with `excerpt: false` it shows only its whole title. An item in a tree is one compact line showing only its title, which ends in an ellipsis when it doesn't fit. The sidebar never scrolls sideways, and the up and down arrows move through group headers and items. Titles and paragraphs show code spans and emphasis; links show as their text and images are left out. An invalid item stays listed, marked, and says what is wrong on hover or focus. Resting the pointer on an item's row for a moment, or Space on the focused row, shows the whole item in a box beside the sidebar without opening it or taking the focus: its title and handle, its properties, its body (scrolling when long) and Open; for a file that can't be parsed, its file name, path and problems instead. A box the pointer opened stays while the pointer is in it and closes once the pointer has left the row and the box. Once Space has opened it, the box moves with the focus as the arrow keys move it (hidden on a group header), until Space, Escape, Enter or the focus leaving the view closes it. Group headers, proposed new items and missing items have none. A click on a row (or Enter) opens the item as a tab (a second click focuses it), titled with its handle and title: its handle and binder, its title to edit, one row per property the binder declares in the settings' order (also those without a value) with a control by type (a select's options, a text field, a number field that takes only a plain decimal number (other text shows why at the field and Save waits until it's fixed), a date picker, a link's target among its binder's items by handle and title, with an Open button; None clears a property the binder doesn't require), and the body as Markdown, which Edit turns into a Markdown editor and Done back. Save (enabled once something changed) writes only the fields you changed into the item's file and leaves the rest of it as it was; Discard goes back to the file. A value the binder refuses is shown at its field with the reason and nothing is written. Editing works in every binder, whatever its access level or locked fields. While you have unsaved changes, a hand edit or an agent's write of the file keeps your changes and says the file changed (the fields you didn't touch follow the file); Save then writes nothing and shows each of your changes beside the file's value, with Take theirs per field and Keep mine, which saves the rest on top of the file as it is now. Closing a tab with unsaved changes asks first. New at the top of a list or tree view opens a new item's tab with the view's filter values already set; the + on a list group also sets the group's value, and the + on a tree row (shown on hover or focus) makes the new item that row's child. Nothing is written until Save, which creates the file, gives the item its handle and turns the tab into the item's tab; in a binder with `naming: free` the new item asks for its file name, and a name the binder refuses shows why at that field. Closing a new item's tab asks only once you have changed something, and a new item's tab doesn't come back after a restart. Delete… in an item tab's menu asks once, naming the item's handle and title, then deletes its file and closes the tab; if the file changed since you asked, nothing is deleted and the tab says so. An invalid item shows each problem at its property and the file's own problems above; a file that can't be parsed shows its problems and its path and says to fix it by hand. The tab follows hand edits of the file, says when the item has been deleted and stays until you close it, and comes back after a restart. An agent's open item proposals show where the items are, in every view of their binder: a proposed new item as a row marked "new", placed and sorted by its proposed values (one the view's filter would hide shows first, saying it is outside the filter); a proposed change or delete as a mark on the item's row, a delete striking its title through; one on an item the view's filter hides shows that item first, saying it is outside the filter, and one on an item whose file is gone (deleted or renamed by hand) shows as a row of its own with the handle and "missing item". A row has a line under it for each open proposal on it, oldest first, each with Approve and Reject (a proposal in conflict says Conflict and offers only Reject), and a click on the mark or the proposed item opens the proposal's tab; an agent's revision shows in place, and an approved new item becomes the item in the same place. Revealing a proposal from Needs me unfolds its group when it is folded and highlights its row. An item's tab shows a banner for each open proposal on the item: the agent, what it proposes, the first line of its reason, Approve, Reject and Open the diff. The open drawers and the binder shown come back after a restart. New binder at the top of the tree, or the + on a drawer's row (shown on hover or focus), asks for a name, a prefix and a folder (both suggested from the name; the folder is inside the items folder or that drawer, and a `/` makes new drawers), and writes a starter `_binder.yaml` you then edit by hand; a folder that already holds Markdown files says how many, since they become the binder's items with an id and a handle written into each, and Create anyway goes ahead; a refusal shows why at its field and writes nothing, and on success the tree opens the drawers down to the new binder and focuses its row. Without an items root the Desk says what the items folder is and offers Choose items folder…; an items folder without binders says to add a folder with a `_binder.yaml` and offers New binder.
- Instructions file: the items of every binder marked `instructions: full` (each item in full) or `instructions: index` (each item's title and first line) are rendered into `<workspace>/.wombat/AGENTS.md`, outside every repo, read-only, with handles and never anything hidden. The service keeps it current: at start, after each of its writes and approvals, and shortly after you edit an item or a `_binder.yaml` by hand. Every new Claude Code agent gets it appended to its system prompt; agents already running keep the one they started with. A binder marked for instructions can't have `access: edit`, so every change to the instructions goes through your approval, and a file over 64 KiB is sent as an index of every binder.
- Agent summaries show what the app's agent list needs: the agent folder's git branch, an excerpt of the agent's own latest message as its chat shows it (a sub-agent's text doesn't show there), when you last sent it a message or answered it, and its open permission requests. A store from an earlier version is upgraded in place when the service starts.
- The service stores the agent's plan and its reasoning as they arrive, instead of skipping them.
- Agent summaries say what a working agent is doing right now (thinking, writing, or running a tool, with the tool's title), read from its log the same way its chat reads it, so the agent list and the chat agree.
- The agent's settings (its model, mode and other options the agent offers) are kept in its history from the start and whenever they change, and `POST /agents/:id/config` changes one. A value the agent doesn't offer is refused before it reaches the agent, and when the agent itself says no, the answer (`agent_error`) carries its reason.
- Every turn in an agent's history ends with a `turn_ended` entry: `error` when the turn failed, `stopped` when the agent's process ended during it.
- Agent summaries say whether the agent's process still runs (`hasProcess`).
- `POST /shutdown` stops every agent (their history is kept) and ends the service.
- An alert stream client that stops reading is disconnected once too many alerts wait for it. The stream doesn't replay: after any reconnect the app reads the agents, the proposals, the binders and items it shows and each open agent's log again.
- A desktop app skeleton with secure defaults: context isolation on, no Node in the renderer, a strict content security policy.
- The desktop app asks for the workspace folder on first start, remembers it in `~/.config/Wombat/settings.json` (only you can read it), and starts the agent service for it when none is running. A service running for another workspace is restarted only when you say so.
- The desktop app reaches the service only through its main process, which holds the token and allows only the service's app routes. Its main process tracks whether it's connecting, connected, reconnecting, incompatible with the service's version, or failed, and reconnects when the service restarts or moves port.
- Quitting while any agent's process runs (done agents too) asks whether to stop them or leave them running ("Don't ask again" turns the question off). The File menu has Switch Workspace and Stop Service and Agents; both ask before stopping agents. Restarting a service from an older version of Wombat asks, then replaces it.
- A desktop notification says when an agent is waiting for you, without anything from the agent in it.
- The app's page is served with a content security policy header and a fresh nonce on every load; UI libraries (Tailwind, Base UI, dockview, Shiki, Monaco's diff editor) run under it.
- The desktop app has a workbench: an activity bar with five activities (Agents, the Desk, and three that say when they arrive), a sidebar, a split, tabbed editor area and a collapsible right sidebar. Agents opens each agent's chat in a tab. The layout (splits, tabs, sidebar widths) reopens per workspace; tabs of deleted agents close, and a layout that can't be restored opens the default without overwriting the saved one.
- The desktop app shows the connection to the service in the status bar. When it's lost (or can't be made), a banner says so with a Restart button, and the views stay as they were, dimmed and unusable, until it's back.
- Zoom: Ctrl+= (also Ctrl+Shift+= and Ctrl+Numpad+) zooms in, Ctrl+- (and Ctrl+Numpad-) zooms out and Ctrl+Numpad0 resets, in steps like VS Code's, between about 40% and 250%. A note shows the new level for a moment; the level is the same in every window and is kept in `settings.json` for the next start.
- Keyboard shortcuts: Ctrl+W closes the active tab, Ctrl+Alt+B shows or hides the right sidebar, Ctrl+Shift+W closes the window and Ctrl+Q quits (asking about running agents as before). Typing in a text field or the editor keeps plain keys for the text.
- CI that lints, type-checks, tests, builds and runs the desktop end-to-end tests on every push and pull request.
- Code in the chat is highlighted in TypeScript, TSX, JavaScript, JSON, shell (`bash`, `sh`), Python, YAML, Markdown, diff, Nix, CSS, HTML and SQL; the diff tab highlights JSON, Python, shell, YAML, Markdown and CSS files besides TypeScript and JavaScript.
- A service from before this app (one that doesn't say which workspace it runs for) shows as incompatible, saying it predates the app; Restart stops it and its agents and starts the app's own service (a service too old to stop that way makes Restart fail, saying how to stop it).
- The Wombat logo: a mark and a symbol, in colour and in one colour, in `app/desktop/assets/brand/`; the mark heads the README.
- The agent service reports when it started and which code it runs: `GET /version` answers `startedAt` and `codeId` (a hash of its source).
- The app knows when the running service is older than the code on disk: it checks on each connect and every minute while connected, so a service that goes stale while the app runs shows it too.

- The app needs Node 26 or newer.
- Quitting with no agent process stops the agent service with the app, without asking. With agents that have a process, the question names how many and offers Keep running, Stop agents and quit, or Cancel; "Don't ask again" remembers the answer (an earlier "Don't ask again" stays Keep). A service kept running at quit is announced by a desktop notification ("The agent service is still running with N agents. Open Wombat to stop it.").
- Restart Service works in every connection state: it asks first only when agents have a process, then stops the service and starts it from the code on disk. A Restart that fails says why in a dialog, whatever the app shows.
- A service of the app's whose process runs but doesn't answer is never joined by a second one: opening Wombat, Restart and Switch Workspace fail instead, naming its pid and how to stop it.
